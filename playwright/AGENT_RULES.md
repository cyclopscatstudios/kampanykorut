# Kampánykörút – Playwright agent rules

Project-specific rules for the `playwright-test-planner`, `playwright-test-generator` and
`playwright-test-healer` agents. The agent files in `.claude/agents/` are generated by
`npx playwright init-agents --loop=claude` and may be overwritten; this file is not touched by
the generator. Where this file conflicts with the generic agent instructions, this file wins.

Regeneration also overwrites `.mcp.json` and `playwright/seed.spec.ts`. Afterwards:

- re-add the "Project rules" block (see the end of this file) to each agent file,
- restore `.mcp.json` to run `node playwright/mcp-server.mjs`,
- restore the seed to import `test`/`expect` from `./helpers/fixtures`.

`git checkout -- .mcp.json playwright/seed.spec.ts .claude/agents` restores all three once committed.

## 1. Scope and hard limits (all agents)

- Never modify application code: `apps/**`, `shared/**`, `tailwind-theme/**`, `build/**`, campaign
  data under `apps/kampanykorut/public/campaigns/**`.
- Never modify `playwright.config.ts`, `package.json`, `yarn.lock` or `.mcp.json`.
- Writable locations: `specs/**` (planner), `playwright/test/**` (generator, healer).
  `playwright/helpers/**` may only be changed when the task explicitly asks for it.
- If the browser cannot be set up (`planner_setup_page` / `generator_setup_page` / `test_run`
  failing before reaching the app), stop and report the exact error. Do not substitute guesses for
  observations. Known cause on Windows: a lowercase drive letter in the MCP server's working
  directory (`d:\` instead of `D:\`) loads `@playwright/test` twice and fails with
  "did not expect test.describe() to be called here". `.mcp.json` starts the server through
  `playwright/mcp-server.mjs`, which normalizes the working directory to avoid this.
- Locally only Chromium is installed; firefox/webkit launch failures ("Executable doesn't exist")
  are environment issues. Run with `--project=chromium` unless told otherwise.
- Report application bugs instead of working around them. Every report separates **observed**
  (seen in the browser, console or network) from **inferred** (read from source).

## 2. Existing conventions to reuse

### Layout

- Config: `playwright.config.ts`, `testDir: ./playwright`, `baseURL: http://localhost:3000`.
  The web server is started with `PLAYWRIGHT=true`, which exposes the test bridge (below).
- Projects: `chromium`, `firefox`, `webkit` (desktop only; mobile projects are commented out).
- Tests live in `playwright/test/`. New tests go in `playwright/test/<suite-kebab>/<scenario-kebab>.spec.ts`.
- Seed: `playwright/seed.spec.ts` (uses the project fixtures, so the page starts at `/menu` with
  debug mode on). Plans: `specs/<area>.md`.
- Component tests are separate (`apps/kampanykorut/playwright-ct.config.ts`) and out of scope.

### Fixtures – always import from the project fixtures

```ts
import { expect, test } from "../../helpers/fixtures";
```

Never import `test` from `@playwright/test` directly in E2E specs. The fixture-provided `page`:

- sets `localStorage.kampanykorut_debugMode = "true"` via an init script (unpublished campaigns
  such as `0001_test_campaign` are visible), and
- has already navigated to `/menu` when the test body starts.

Extra fixtures (`playwright/helpers/fixtures.ts`, backed by `playwright/helpers/testBridge.ts`):

| Fixture | Use |
|---|---|
| `seedCampaign(campaignId, partyId?, candidateId?)` | Create a fresh session at the start of a campaign; returns `{ sessionId, state }` |
| `playCampaign(campaignId, partyId?, candidateId?, answerPlan?)` | Play the whole campaign programmatically; `answerPlan` maps questionId → answerId, others fall back to the first answer |
| `getCampaignState()` | Read the current `CampaignState` from the app |

Use the bridge to reach a state quickly (e.g. mid-game or ended) and the UI to test the behaviour
under test. Do not use the bridge to perform the action the scenario is verifying.

### Locators

Priority: `getByTestId` → `getByRole` with accessible name → `getByText`. No CSS/XPath chains, no
`nth()` unless order is the thing under test. Known test ids:

- `menuItem-<id>` (e.g. `menuItem-settings`), `saveButton`, `showAdvisorFeedback`, `changeLanguage`
- `partySelector`, `candidateSelector`; dropdown options use the option value as test id
  (`green_party`, `emma_wilson`, `hu`)
- question card root uses the questionId as test id

### Language

- UI language comes from `localStorage.kampanykorut_language` (`en` | `hu`), default `en`. It does
  not follow the browser locale. `campaign.spec.ts` sets `test.use({ locale: "hu-HU" })`, which
  affects browser locale (formatting) only; some game/end-result copy is Hungarian regardless.
- To test Hungarian UI, switch through settings (as `settings.spec.ts` does) or set
  `kampanykorut_language` with `page.addInitScript` before navigation.
- Copy Hungarian strings in assertions exactly, including accents
  (`Választási térkép`, `Statisztikák`, `Előzmények`).

### Style

- Match the existing specs: no per-step comments; only the `// spec:` and `// seed:` header lines
  are kept so tests can be traced back to the plan.
- Web-first assertions (`await expect(locator).toBeVisible()` etc.). No `waitForTimeout`, no
  `networkidle`, no `force: true` unless the scenario is specifically about it.
- Each test must be independent; never rely on state from another test.

## 3. Domain model (needed by the planner)

### Campaigns

Campaign data: `apps/kampanykorut/public/campaigns/<folder>/` (`election_config.json`,
`manifest.json`, party folders). Campaign **ids** differ from folder names (folder
`2022_beke-vs-remeny` → id `2022_beke_vs_remeny`). Known ids used in tests:

| id | sides used in tests |
|---|---|
| `2026_tavaszi_szel` | `tisza` / `magyar_peter` |
| `2022_beke_vs_remeny` | `fidesz` / `orban_viktor`, `ellenzeki_osszefogas` / `marki_zay_peter` |
| `0001_test_campaign` | `green_party` / `emma_wilson`, `red_party` (unpublished, debug mode) |

`2018_a-g-nap-utan` is work in progress; treat it as possibly incomplete.

Invariants from existing tests: a full campaign is 32 questions/rounds; end results distribute
199 seats in total; no internal party ids starting with `_` appear in results.

### Routes and user flows

| Route | Purpose |
|---|---|
| `/menu` | Main menu (new game, load game, settings, about, privacy) |
| `/new-game` → `/new-game/classic` | Mode and campaign selection |
| `/new-game/classic/sides/:campaignId` | Party then candidate selection; candidate is disabled until a party is chosen; changing party clears candidate |
| `/game/:id?sessionId=…` | Main game: question card, answers, Continue, map, advisor feedback, header stats |
| `/game/:id/end-results?sessionId=…` | End results: election map, statistics (seats), history ("32 forduló") |
| `/load-game` | Saved sessions list |
| `/settings` | Language, advisor feedback; Save is disabled until something changes; success toast |
| `/news`, `/news/:number`, `/about`, `/privacy` | Secondary pages |

Primary journey: menu → new game → classic → pick campaign → pick party and candidate → answer
32 questions (each answer changes the simulated state) → end results. Secondary journeys: save the
game, leave, resume from Load game; reload mid-game; open an ended session.

### State persistence (localStorage)

All keys are prefixed `kampanykorut_`. Session-scoped keys are suffixed with `-<sessionId>`.

| Key | Content |
|---|---|
| `kampanykorut_currentSessionId` | Active session |
| `kampanykorut_campaignState-<sid>` | Campaign state (player side, round, results, `isEnded`) |
| `kampanykorut_turnHistory-<sid>` | Turn history |
| `kampanykorut_savedSessions` | Manually saved sessions |
| `kampanykorut_autoSaveRegistry` | Autosaves |
| `kampanykorut_settings` | User settings (advisor feedback, etc.) |
| `kampanykorut_language` | UI language (`en` / `hu`) |
| `kampanykorut_debugMode` | Debug flag (set to `true` by the fixtures) |

Storage write failures surface through the storage error notifier (toast). Persistence scenarios
should cover: reload at each stage, resume via saved session, stale/unknown `sessionId`, cleared or
corrupted storage, and settings surviving reload. Inspect real keys in the browser before writing
expectations; the table above was derived from source and may drift.

### Responsive UI

Breakpoints come from `useMediaQuery`: `min-width: 768px` (main layout switch: app layout, game
view, question card, header, advisor modal, end results, campaign selector) and `min-width: 440px`
(game header). Test at least 390×844 (phone), 767 vs 768 (breakpoint edge) and a desktop width.
Since no mobile project is configured, mobile scenarios set the viewport/device in the test with
`test.use({ viewport: … })` or `test.use({ ...devices["Pixel 5"] })`.

## 4. Planner rules

- Read the existing specs and fixtures first; do not plan scenarios that duplicate existing
  coverage unless they add a UI-level check.
- Every scenario states its starting state: either "fresh via fixture `page` (at `/menu`, debug
  mode on)" or a bridge seed call (`seedCampaign` / `playCampaign` with explicit ids).
- Use concrete campaign/party/candidate ids from the table above. Prefer `0001_test_campaign` for
  generic UI behaviour and real campaigns for content-specific checks.
- Tag anything not observed in the live app as `[UNVERIFIED]`.
- Put bugs in a separate "Observed issues" section at the end of the plan, never as expected
  behaviour inside a scenario.

## 5. Generator rules

- One test per file, describe = top-level plan section (without ordinal), title = scenario name
  (without ordinal), as in the generic instructions.
- Use the fixtures and locator priorities above; replace raw locators from the generator log with
  the project test ids where one exists.
- If a step cannot be performed as the plan describes, do not invent a different flow: write the
  test according to the plan, and report the discrepancy.

## 6. Healer rules – do not hide application bugs

Classify every failure before editing:

1. **Test defect** (outdated locator, missing wait, wrong starting state, typo in expected copy that
   the plan did not intend) → fix the test.
2. **Application defect** (behaviour contradicts the plan, the existing invariants, or an obvious
   user expectation; console errors; crashes; data loss) → do **not** change the test to pass.
3. **Environment** (server not starting, browser setup failing, flaky infrastructure) → stop and
   report.

Forbidden ways of making a test pass:

- `test.skip`, `test.fixme`, `test.fail`, `test.only`, conditional skips, or deleting the test
- removing or commenting out assertions, or replacing specific assertions with weaker ones
  (`toBe(x)` → `toBeTruthy()`, exact text → broad regex, count → `> 0`)
- changing expected values to whatever the app currently returns without evidence that the plan
  was wrong
- wrapping assertions in `try/catch`, `.catch(() => {})`, or `expect.soft` to swallow failures
- raising timeouts beyond the config defaults to mask slowness, `waitForTimeout`, `force: true`
- editing fixtures, config, or application code

For application defects: leave the test failing as it is and report it with test file, failing
step, observed vs expected, console/network evidence and repro steps. This overrides the generic
instruction to mark tests with `test.fixme()`. Regex locators are acceptable only for genuinely
dynamic data (session ids, generated numbers), never for expected outcomes.

Final healer report lists every test as: fixed (with the reason), still failing – app defect,
or still failing – environment.

## Project rules block for the generated agent files

Paste this at the top of the body (after the front matter) of each file in `.claude/agents/`
after regenerating them:

```markdown
## Project rules

Before doing anything else, Read `playwright/AGENT_RULES.md` and follow it. It contains the
Kampánykörút conventions, domain model and limits, and takes precedence over the generic
instructions below wherever they conflict.
```

For `playwright-test-healer.md`, append to the block:

```markdown
In particular, section 6 replaces the generic `test.fixme()` and "do the most reasonable thing
possible to pass the test" guidance: never weaken, skip or quarantine a test to hide an
application defect; leave it failing and report it.
```
